# HTTP-контракт

Открытый интерфейс, по которому программа работает с сервером. Реализовать его может любая система: 1С (расширение — когда появится доступ к конфигуратору), трекер задач, свой сервис. Программа при этом не меняется.

Тела запросов и ответов — [файл обмена](format.md). Тот же документ можно сохранить в файл и передать без сети.

## Общее

- **Адрес** — любой базовый URL из профиля подключения, например `http://сервер/база/hs/gantt/v1`.
- **Формат** — `Content-Type: application/json; charset=utf-8`.
- **Авторизация:**
  - HTTP Basic служебного пользователя — логин и пароль хранятся в диспетчере учётных данных Windows (keyring), не в настройках;
  - или без авторизации, если сервер так настроен.

  В локальной сети по HTTP пароль Basic передаётся почти открытым текстом — желателен HTTPS.
- **Версия API** — в пути (`/v1`). В 1.x только добавляются необязательные поля.

## GET /ping

Проверка связи и возможностей сервера. Ответ — служебный JSON, не файл обмена:

```json
{
  "api": "1.0",
  "schemaVersions": ["1.0"],
  "server": { "name": "ГантИнтеграция", "version": "1.0.0" },
  "source": "1C:УправлениеITОтделом",
  "sourceName": "[имя базы]",
  "user": "[служебный пользователь]",
  "readOnly": false,
  "capabilities": { "incremental": true, "import": true }
}
```

Программа показывает это в «Проверить соединение» и по `capabilities` решает, что доступно: инкременты, отправка правок.

## GET /export

- **Без параметров** — документ `full`.
- **`?changedSince=<cursor>`** — документ `incremental` с изменениями после метки.

  Если метка устарела или неизвестна, сервер вправе вернуть `full`: программа смотрит на `meta.kind`, а не на то, что просила. `cursor` непрозрачен для программы — это строка, которую она только возвращает.

## POST /import

- **Тело** — документ `changes`.
- **Ответ 200** — документ `results`: ровно один результат на каждый `changeId`.

Каждая правка обрабатывается отдельно. Одна неудачная не отменяет остальные.

| `result` | Когда | Что в ответе |
|---|---|---|
| `applied` | записано | `currentVersion` — новая версия узла |
| `conflict` | значение в источнике уже не то, от которого сделана правка | `currentValue`, `currentVersion` |
| `rejected` | нельзя записать | `reason`: «поле не разрешено», «нет прав», «недопустимый переход статуса», «узел удалён»… |

**Повтор безопасен.** Сервер помнит результат по `changeId`: если программа повторит запрос после обрыва связи, та же правка второй раз не применяется, а возвращается прежний результат.

## Ошибки

| Код | Когда | Тело |
|---|---|---|
| 400 | документ не прошёл проверку | `{"error": "…", "details": ["…"]}` |
| 401 / 403 | нет авторизации или прав | `{"error": "…"}` |
| 413 | слишком большой запрос | |
| 500 / 503 | ошибка сервера, база недоступна | `{"error": "…"}` |

При сетевой ошибке или 5xx программа переходит в режим «Офлайн»: работает на кэше и повторяет запрос с нарастающей паузой.

## Для того, кто будет делать сервер (в том числе расширение 1С)

- **Отслеживание изменений** для `changedSince`. Варианты:
  - план обмена;
  - регистр-журнал изменений через подписки на события;
  - дата изменения объекта.

  Критерии выбора:
  - видны ли удаления (их нужно отдавать в `deleted`);
  - работают ли несколько программ с разными `cursor` одновременно;
  - учитываются ли изменения, пришедшие через обмен данными.

  Дата изменения удалений не видит. Один узел плана обмена со снятием регистрации после чтения не подходит для нескольких программ.
- **Запись правок:**
  - только через объектную модель;
  - каждый объект — в своей транзакции;
  - только поля из белого списка (его же отдавать в `editable`).
- **Конфликт** — когда текущее значение поля в источнике отличается от `oldValue`. Сравнивать только версию объекта не стоит: она меняется при любой записи, даже другого поля, — будут ложные конфликты.
- **Журнал:** каждое применённое изменение записывать с полями когда, объект, поле, было/стало, `author`, `machine`, `comment`.
- **Смена статуса** — через штатный механизм источника, если он есть (история, уведомления), а не прямой записью поля.

## Тестовый сервер

Тестовый сервер реализует этот контракт на демо-данных из [examples/](../examples/). Написан на стандартной библиотеке Python (`http.server`) — без FastAPI и других зависимостей, поэтому встроен прямо в программу.

- **Из программы:** «Сервер → Подключение к серверу → Запустить тестовый сервер на этом ПК». Слушает только `127.0.0.1`, данные хранит в `%LOCALAPPDATA%\Гант\test-server.json` — переживают перезапуск.
- **Отдельно:** `python -m gantt.mock_server --port 8765 [--auth логин:пароль] [--churn 60] [--fail 0.2] [--delay 2] [--readonly] [--data файл.json]`.

Что умеет имитировать:
- «жизнь» источника — раз в `--churn` секунд переносит срок или закрывает задание, это приходит инкрементом;
- конфликты (значение уже не то, что было при загрузке) и отказы (поле не разрешено, узел удалён, только чтение);
- повтор отправки — тот же ответ по `changeId`;
- Basic-авторизацию, задержки и сбои 503.

Программа проверяется против него автоматически (`tests/test_http.py`).
