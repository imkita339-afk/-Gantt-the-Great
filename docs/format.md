# Файл обмена Ганта (gantt-exchange), схема 1.0

Один документ для всех случаев: файл на диске, ответ и тело HTTP-запроса. Программа внутри работает только с ним, а все прочие форматы (Excel, CSV, MS Project…) переводятся в него и из него — см. [import-export.md](import-export.md).

- Схема: [schema/gantt-exchange.schema.json](../schema/gantt-exchange.schema.json) (JSON Schema 2020-12).
- Примеры: [examples/](../examples/).

## Общие правила

- **Кодировка UTF-8.** Программа читает файл и с BOM (1С может его записать), а пишет без BOM.
- **Дата** — `ГГГГ-ММ-ДД`. **Дата и время** — ISO 8601 со смещением: `2026-09-24T10:04:00+07:00`. Пустое значение — `null` или отсутствие поля.
- **Идентификаторы** — любые непустые строки: GUID, код, номер. Уникальны в пределах своего списка.
- **Узлы** — плоским списком, связь через `parentId`. Так удобно передавать инкременты.
- **Имя файла.** Рекомендуется `*.gantt.json`, но программа принимает любой `.json` и узнаёт формат по содержимому (`"format": "gantt-exchange"`), а не по расширению. Ассоциацию файлов программа не регистрирует: `.json` слишком общий тип, а своё расширение пришлось бы учить писать все системы-источники.

## Документ целиком

```json
{
  "format": "gantt-exchange",
  "schemaVersion": "1.0",
  "meta": { "source": "…", "exportedAt": "…", "kind": "full" },
  "dictionaries": { "levels": […], "statuses": […], "people": […] },
  "nodes": [ … ],
  "deleted": [ … ],
  "changes": [ … ],
  "results": [ … ]
}
```

Какие разделы заполнены, определяет `meta.kind`:

| `kind` | Что это | Обязательно | Нельзя |
|---|---|---|---|
| `full` | снимок всех данных | `dictionaries` (с `levels`), `nodes` | `deleted`, `results` |
| `incremental` | изменения с прошлого раза | `nodes` (можно пустой), `meta.changedSince`, `meta.cursor` | `changes`, `results` |
| `changes` | правки из программы на отправку | `changes` | всё прочее |
| `results` | ответ источника на правки | `results` | всё прочее |

`full` может нести и `changes`: это снимок с несохранёнными в источнике правками. Так программа сохраняет работу без сервера и не теряет очередь.

- В `nodes` такого снимка — **значения источника**, правки — только в `changes` (в том числе цвет проекта: у себя программа хранит его как правку, в источник цвет не отправляет).
- Открывая снимок, программа берёт из `changes` в свою очередь те правки, которых у неё ещё нет. Поэтому снимок можно передать коллеге, а открытие снимка не «съедает» правки того набора, из которого он сделан.

## meta

| Поле | Обяз. | Описание |
|---|---|---|
| `source` | да | Тип источника: `1C:УправлениеITОтделом`, `excel:ProjectsToGanttExport`, `tracker:helpdesk`… |
| `sourceName` | | Экземпляр: имя базы, файла, очереди. `source` + `sourceName` — это **набор данных**: у каждого свой кэш и своя очередь правок. |
| `title` | | Заголовок для окна программы. |
| `exportedAt` | да | Когда сформирован документ. |
| `exportedBy` | | Кто сформировал. |
| `kind` | да | `full`, `incremental`, `changes`, `results`. |
| `changedSince` | для incremental | `cursor` документа, от которого собраны изменения. |
| `cursor` | для incremental | Метка для следующего запроса. Программа её не разбирает, только возвращает. |
| `defaultEditable` | | `editable` для узлов, у которых он не указан. |
| `generator` | | `{ "name", "version" }` программы, создавшей документ. |

## dictionaries

Всё, что зависит от конкретной системы, приходит здесь, а не зашито в программу. Программа может только переопределить отображение (цвет, видимость) и запомнить это.

- **`levels`** — уровни иерархии `{id, name, order, color?}`. Число уровней любое, минимум один; `order` 1 — верхний. Плоский список — один уровень.
- **`statuses`** — `{id, name, kind, color?, order?}`. Название любое; `kind` задаёт логику и цвет по умолчанию:

| `kind` | Смысл | Цвет по умолчанию |
|---|---|---|
| `notStarted` | не начато | серый `#8A9099` |
| `inProgress` | в работе | синий `#2F5FD0` |
| `onHold` | приостановлено, ждёт | серый `#8A9099` |
| `release` | в релизе, на проверке | фиолетовый `#7452C9` |
| `done` | выполнено | зелёный `#3F8F66` |
| `cancelled` | отменено | серый, зачёркнуто |
| `overdue` | просрочено (если источник хранит так) | оранжевый `#D1560B` |

  «Просрочено» программа вычисляет и сама для любого источника: план окончания прошёл, а статус не `done` и не `cancelled`.

- **`priorities`, `urgencies`, `impacts`** — шкалы `{id, name, order, color?}`; чем больше `order`, тем выше.
- **`categories`** — `{id, name, color?}`.
- **`people`** — `{id, name, fullName?, email?}`; `name` — как показывать («Аналитик 1»).
- **`customFields`** — пользовательские поля `{id, name, type, values?}`. Типы: `string`, `number`, `date`, `dateTime`, `boolean`, `enum` (для `enum` обязателен список `values`). По ним работают колонки, подсказки и фильтры.

## nodes

| Поле | Описание |
|---|---|
| `id` | обязательно, уникален |
| `parentId` | родитель или `null` |
| `level` | обязательно, `id` из `levels` |
| `order` | порядок среди соседей, как в источнике |
| `number` | номер или код для показа: «5012», «1.2» |
| `name` | обязательно |
| `description` | описание |
| `executors` | список `id` из `people` |
| `initiator` | `id` из `people` |
| `planStart`, `planEnd` | план |
| `factStart`, `factEnd` | факт |
| `percent` | 0–100 |
| `status`, `priority`, `urgency`, `impact`, `category` | `id` из справочников |
| `color` | цвет полосы `#RRGGBB`, например у проекта; нет — программа подберёт пастельный сама |
| `milestone` | веха — событие без длительности |
| `predecessors` | зависимости `[{id, type: FS/SS/FF/SF, lagDays}]` |
| `url` | ссылка «Открыть в источнике» (`https://…`, `e1c://…`) |
| `custom` | значения пользовательских полей: `{ "taskKind": "incident" }` |
| `version` | версия данных в источнике — для конфликтов |
| `editable` | какие поля источник разрешает менять |

**Что программа считает сама, если источник не прислал:**
- процент родителя — по детям: выполненные / все («3/5»);
- исполнители родителя — по детям («Аналитик 1 +4»);
- полоса родителя без своих дат — сводная по детям;
- признак «просрочено».

**Правила `editable`:**
- указан у узла — действует он;
- не указан, но есть `meta.defaultEditable` — действует он;
- нет ни того, ни другого — источник ничего не ограничивает;
- пустой список — узел только для чтения.

Программа в любом случае даёт менять только те поля, для которых у неё есть редактор.

## deleted

Только в `incremental`: `id` узлов, удалённых в источнике. Узел удаляется вместе с потомками, если их нет в этом же документе.

## changes

| Поле | Обяз. | Описание |
|---|---|---|
| `changeId` | да | уникальный id правки (UUID); по нему приходит результат |
| `nodeId` | да | узел |
| `field` | да | `planEnd`, `status`… или `custom.<id>` |
| `oldValue` | | значение в данных источника, от которого сделана правка |
| `newValue` | да | новое значение |
| `baseVersion` | | `version` узла на момент правки |
| `author` | | ФИО того, кто нажал «Подтвердить» |
| `machine` | | имя ПК |
| `at` | да | когда сделана правка |
| `comment` | | комментарий в журнал |

Тип значения проверяется по полю: даты — `ГГГГ-ММ-ДД`, `percent` — 0–100, `executors` — список.

## results

| Поле | Обяз. | Описание |
|---|---|---|
| `changeId` | да | к какой правке |
| `result` | да | `applied` — записано; `conflict` — в источнике уже другое значение; `rejected` — отказ |
| `currentValue` | для conflict | что сейчас в источнике |
| `currentVersion` | | версия узла сейчас |
| `reason` | для rejected | причина для человека: «поле не разрешено», «нет прав», «недопустимый переход статуса» |

## Как программа применяет документы

- **`full`** заменяет данные набора. Правки из очереди сохраняются и сверяются с новыми значениями (см. «Конфликты» в [architecture.md](architecture.md)).
- **`incremental`**: каждый узел из `nodes` заменяется целиком — это его текущее состояние, а не заплатка; `deleted` удаляются; `cursor` запоминается.
- **`changes`** показывается списком «было → стало» и попадает в очередь только после подтверждения пользователем.
- **`results`** закрывает очередь:
  - применённые правки уходят;
  - конфликты предлагают выбор «оставить моё / взять из источника»;
  - отказы показываются с причиной.

## Проверка

При каждом открытии — две проверки. Любая ошибка — и текущие данные не меняются.

1. **По схеме:** структура, типы, форматы дат, обязательные поля.
2. **Смысловая** — то, что схемой не выразить:
   - `id` узлов и справочников не повторяются;
   - `parentId` указывает на существующий узел, циклов нет;
   - ссылки на справочники существуют (уровень, статус, люди, шкалы);
   - `custom` — только объявленные поля, значения по их типу;
   - `predecessors` ссылаются на существующие узлы;
   - `changeId` не повторяются.

   Для `incremental` ссылки на узлы, которых нет в документе, проверяются по уже загруженным данным.

**Предупреждения** (данные загружаются, но о них сообщается в отчёте об импорте):
- начало позже окончания;
- уровень ребёнка не глубже уровня родителя;
- обрезанные названия («...»);
- одинаковые название, исполнитель и даты.

**Отчёт об ошибках** показывает все ошибки сразу и по-русски. Вместо `nodes[412].planEnd` он называет узел и поле: `Узел № 5012 «Название» (id), поле «План окончания»: ожидалась дата ГГГГ-ММ-ДД, в файле «23.09.26»`.

## Версии схемы

- `schemaVersion` — «основная.дополнительная».
- В 1.x только добавляются необязательные поля. Документ более новой 1.x программа откроет: незнакомые поля пропустит с предупреждением.
- 2.0 и выше — несовместимо: программа откажет с понятной причиной.
